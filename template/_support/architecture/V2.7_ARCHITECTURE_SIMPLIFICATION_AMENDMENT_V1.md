# V2.7 Architecture Simplification Review & Amendment V1

**Date:** 2026-10-08  
**Status:** PROPOSED FOR IMMEDIATE GOVERNANCE ADOPTION  
**Scope:** V2.7 architecture execution model, workstream dependencies, complexity controls, acceptance cadence  
**Does not do:** modify product code, change the 41 capability meanings, erase historical evidence, or declare unproven capability PASS.

## 1. Executive decision

V2.7's architectural direction remains valid:

> **Stable Core + Game Adaptation + Pattern Library → Assembled Game Site → Independent Acceptance**

The problem is not the target architecture. The implementation and evidence process has become too complex relative to the product value currently proven.

The current system has accumulated overlapping mechanisms such as bounded-development readiness, implementation-accepted-for-continuation, formal gates, repeated 47-case browser runs, WebKit-to-Safari evidence bridging, large protected-file hash inventories, interface binding ledgers, repeated contract identity checks, and several state vocabularies describing nearly the same thing.

Each mechanism has a defensible local purpose, but together they create a system where engineering increasingly serves the evidence process instead of producing visibly better game sites.

**V2.7 therefore adopts a simplification correction before further runtime/schema expansion.**

## 2. What remains unchanged

### 2.1 Stable Core remains narrow

Core continues to own only portable technical guarantees:

- Page Inventory publication truth;
- exact route/output reconciliation;
- SEO/canonical/robots/sitemap/structured-data foundations;
- media validation/rendering seams;
- search technical seam;
- optional ad seam;
- accessibility primitives;
- fail-closed validation/build behavior;
- legal / identity / production-residue safety.

Core must not decide game taxonomy, page coverage, visual identity, player priorities, content strategy, media rights, or homepage editorial composition.

### 2.2 Game Adaptation remains first-class

Game Adaptation remains the missing bridge exposed by V2.5–V2.6.5. It owns project-specific terminology, taxonomy, player tasks, visual evidence, theme/token values, media need/use decisions, search rationale, related-content rationale, update/freshness basis, and human review responsibility.

### 2.3 Pattern Library remains separate from Core

Patterns compose Core; they do not fork or duplicate it.

V2.7 initial Pattern scope remains limited to:

1. **Wiki / Hub**
2. **Task Guide**
3. **Media-rich Article**

No page builder, layout DSL, pattern marketplace, theme engine, or five-reference-site forks are authorized.

### 2.4 Independent assembled-site acceptance remains mandatory

Core tests do not prove game recognition, useful player journeys, semantic media quality, truthful content depth, whole-page visual quality, ad obstruction, or assembled keyboard/overflow behavior.

## 3. Execution architecture is reduced to four operational surfaces

The six-layer blueprint remains useful as an explanatory model, but daily engineering shall use only:

```text
1. Core
2. Adaptation
3. Patterns
4. Acceptance
```

Product Contract / Capability Registry is cross-cutting governance. Assembled Game Site is an output. Release Governance is an acceptance responsibility, not a runtime subsystem.

## 4. Dependency correction: Safari/browser release evidence must not block unrelated Core seams

The current roadmap effectively allows incomplete WS-06A browser evidence to block formal WS-03 acceptance, which then blocks WS-04A and WS-05. This is invalid coupling.

Share/OG metadata, media schema, search normalization, and freshness semantics do not logically depend on Safari keyboard behavior.

### New rule

A work item is verified at the level of evidence relevant to that work item.

For non-browser-specific Core seams, acceptance requires:

- schema/unit tests;
- integration/output tests;
- `npm run check`;
- adopted build/validate where applicable;
- targeted browser test only when the changed behavior is browser-visible or browser-dependent.

It does **not** require complete real-Safari release evidence.

Browser-specific behavior such as navigation, focus, keyboard, resize, overflow, or browser lifecycle still requires relevant browser evidence before that capability is considered proven.

Full browser coverage, including representative real Safari checks, belongs at assembled-site/release acceptance.

## 5. Amended workstream dependency model

Existing workstream IDs are preserved.

```text
WS01 ─→ WS02 ─→ WS03 technical interfaces
              └──────────────┐
WS01 ───────────────────────→ WS04A minimal adaptation contract
                              │
WS03 relevant interface ─────┘
                              ↓
                         WS05 patterns
                              ↓
                  two-game vertical proof
                              ↓
                         WS04B instance proof
                              ↓
                         WS06B assembled acceptance
                              ↓
                         WS07 real adoption
                              ↓

```

WS-06A browser infrastructure runs **in parallel**.

It blocks final AX-01/AX-03 proof, WS-06B closure where applicable, and release acceptance. It does not block unrelated WS-03 media/share/search/freshness interfaces, WS-04A design, or WS-05 composition work.

## 6. Existing WS-03 work is preserved, but evidence repetition stops

Current candidate implementations for 03A visual roles, 03B media/video, 03C share media, 03D search, and 03D freshness are not discarded.

Historical failures and continuation reviews remain evidence.

Going forward:

1. do not rerun the unchanged 47-case matrix merely to authorize the next non-browser slice;
2. do not recalculate thousands of protected-file hashes for every slice;
3. do not invent another continuation status;
4. perform one consolidated review against the amended acceptance model;
5. if source has not changed, reuse valid existing test evidence;
6. rerun only evidence materially affected by source changes.

No historical result is rewritten.

## 7. Evidence system simplification

### Per implementation slice

Required by default:

```text
baseline commit / source identity
allowed changed files
git diff --name-only
git diff --check
targeted unit/integration tests
npm run check
relevant targeted browser evidence when applicable
```

### Workstream closure

- full check;
- adopted validate/build where applicable;
- representative browser evidence for UI behavior;
- scope diff review;
- affected capability mapping;
- independent review.

### Release candidate

Only at release-level acceptance should V2.7 require:

- full browser matrix;
- representative real Safari evidence;
- 41/41 capability reconciliation;
- REF regression;
- real project adoption;
- cross-version capability delta;
- final triad compatibility.

### Large protected-file hashing

Routine hashing of 6,000+ protected files is discontinued. Git is the primary change ledger:

- exact baseline commit/tree where available;
- `git status`;
- `git diff`;
- changed-file allowlist;
- focused hashes only for a small number of truly normative artifacts.

Large hash inventories are reserved for packaging/release integrity or exceptional forensic work.

## 8. Capability Registry usage is reduced during development

The 41 capability IDs remain unchanged.

During normal development a slice records only:

- affected capability IDs;
- evidence produced for those IDs;
- known non-claims.

Do not re-evaluate all 41 IDs after every small change.

Full 41/41 reconciliation occurs at WS-08/release.

## 9. visualRoles correction

Current candidate interface:

```text
font: editorial | interface
density: comfortable | compact
shape: square | soft
state: lifted | quiet
```

is technically small and may remain for compatibility, but it must **not become the long-term Game Adaptation model**.

Treat these values as optional convenience presets/compatibility helpers.

The durable Core contract is semantic CSS/design-token surfaces, such as display font, body font, shell spacing, section spacing, surface radius, control radius, surface depth, motion strength, hover treatment, and content density.

A real game may provide values derived from verified visual evidence.

No additional visual enum families may be added until real multi-game adoption proves they are genuinely reusable.

Do not evolve this into a theme engine, preset registry, genre-to-theme mapper, or visual DSL.

## 10. liveStatus correction

The separation of `publishedAt`, `updatedAt`, source `accessedAt`, and patch/version context is retained.

`liveStatus / observed-live` is **experimental** until a real V2.7 adoption demonstrates material product value.

Rules:

- do not expand the model;
- do not create telemetry infrastructure;
- do not make it a required adaptation field;
- do not make project completion depend on it;
- do not infer “Live now”;
- at V2.7 release review, retain it based on real adoption or explicitly defer/remove it.

The primary requirement remains: never display unsupported Live / Popular / Trending claims.

## 11. WS-04A must not become a large runtime schema

The A0–A9 method is useful as an SOP/adoption checklist. It must not be translated one-for-one into runtime JSON/Zod fields.

Method evidence such as why a pattern was selected, why video was excluded, why search is enabled, who approved a rights/use decision, why a related page is useful, or what evidence supports a visual choice should normally remain project decision documentation.

Runtime stays thin and prefers existing authorities:

- Page Inventory;
- `game.config.ts`;
- `theme.css`;
- content;
- facts;
- media manifest;
- existing feature flags.

Create a new runtime adaptation field only when a real Pattern implementation requires it.

Do not create a speculative all-in-one `game-adaptation.schema.ts`.

Pattern IDs should not be frozen before WS-05 produces real Pattern components.

## 12. WS-05 implementation is deliberately small

V2.7 first Pattern Library contains only:

### Wiki / Hub
Orient users, expose real categories/objects, and reach useful destinations.

### Task Guide
Answer a concrete player question, show actionable steps/decision basis, and provide recovery/next-step guidance when useful.

### Media-rich Article
Support long-form reading with real media, using cover/figure/gallery/video/TOC only when useful.

Shared optional modules may include:

- Quick Answer;
- Steps;
- Comparison;
- Figure/Gallery;
- TOC;
- FAQ;
- Related / Next Step.

Every module is optional unless the selected pattern's job requires it.

No block DSL or arbitrary module registry is authorized.

## 13. Product proof moves earlier

The main inherited risk from V2.5–V2.6.5 is building a technically excellent system before proving final product quality.

Therefore WS-05 must produce an early **two-game vertical proof** before broader abstraction work.

Use the same V2.7 Core and Pattern code to render representative routes for:

1. Bomb Farm;
2. War of Genesis.

The proof must show material differentiation in:

- visual identity;
- media treatment;
- page rhythm;
- player task;
- taxonomy/navigation;
- article composition.

A reviewer should be able to identify which game/site they are viewing without relying only on the logo/title.

This is a product milestone, not a new governance state or capability ID.

If both sites still look like the same Starter with different colors, stop adding abstractions and repair Adaptation/Pattern composition first.

## 14. Browser evidence cadence

### Every code slice
- unit/integration tests;
- `npm run check`;
- targeted browser only if behavior warrants it.

### Workstream closure
- Chromium + Firefox + WebKit representative surfaces where relevant.

### Release / assembled acceptance
- complete supported browser matrix;
- representative real Safari keyboard/focus/overflow checks;
- mobile/desktop visual review.

Real Safari remains important, but moves to the correct product/release boundary.

## 15. Codex implementation rules for V2.7

### Simplest implementation first

Codex must prefer:

- an existing component over a new abstraction;
- one explicit adapter over a registry;
- a data field only when a real consumer exists;
- project documentation over runtime schema for non-runtime decisions;
- direct composition over a DSL.

### No speculative framework building

Unless explicitly authorized, do not add:

- provider registries;
- strategy/factory layers;
- plugin systems;
- page builders;
- layout DSLs;
- theme engines;
- generic state machines;
- duplicate data authorities.

### Two-use rule

A reusable abstraction should normally have at least two real consumers/use cases, unless it is a safety boundary, accessibility guarantee, or an already-required narrow provider-neutral seam.

### Owner-readable review

Every implementation result must explain:

```text
What changed
Why it is needed
What did NOT change
How a real game uses it
Why this is the simplest viable design
```

If this cannot be explained clearly, the implementation is not ready for acceptance.

## 16. State vocabulary simplification

Do not create further custom states.

For future work, report:

```text
Decision: ACCEPT / REVISE / BLOCK
Scope: TECH / PRODUCT / RELEASE
```

Examples:

```text
ACCEPT — TECH SCOPE
BLOCK — PRODUCT SCOPE
```

Existing historical state labels remain in historical records and are not rewritten.

## 17. Handling the current WS-06A Safari blocker

Current Safari proof remains zero and previous browser evidence remains historically valid.

The amended interpretation is:

- AX-01 / AX-03 are still not fully proven;
- release acceptance is still blocked until required Safari evidence exists;
- unrelated Core interface development is no longer blocked;
- do not repeatedly rerun the same unchanged 47-case evidence;
- next full browser run occurs after meaningful assembled-site/UI source changes or at the appropriate acceptance boundary.

No failure is waived. Only the dependency is corrected.

## 20. Architecture guardrails

V2.7 should be rejected as over-engineered if any of the following becomes true:

1. a real game needs multiple duplicate authorities for the same fact;
2. Adaptation becomes a second Page Inventory/media database;
3. a Pattern owns SEO, route publication, media validation, or accessibility logic;
4. visual identity is constrained primarily by generic preset enums;
5. routine feature work requires full 41-capability or 47-browser re-certification;
6. Codex needs several documents merely to determine whether it may edit one small interface;
7. more effort is spent proving unchanged files than reviewing changed behavior;
8. the same Core/Patterns cannot produce two obviously different game sites without project-specific component forks.

## 21. Success test for the simplified V2.7

V2.7 is on the right path when:

- a new game can be adopted without changing Core;
- game-specific choices mostly live in content, media, theme tokens and thin adaptation decisions;
- three Patterns cover initial commercial-site needs without a page builder;
- Bomb Farm and War of Genesis share Core/Patterns while looking and reading materially differently;
- media, share, search and freshness seams remain understandable in small files;
- Codex changes are explainable to the product owner without reading thousands of lines of evidence;
- full browser/capability reconciliation exists at the correct acceptance/release boundary;
- V2.6.5 safety gains remain intact.

## 22. Amendment decision

**Recommended decision: ADOPT.**

This amendment changes execution/governance and narrows some candidate contract status. It does not erase implemented code or historical evidence.

Next sequence:

```text
Adopt simplification amendment
→ consolidated WS03 TECH review
→ simplified WS04A binding
→ minimal WS05 patterns
→ Bomb Farm + War of Genesis vertical proof
→ assembled acceptance
```

That sequence directly tests the reason V2.7 exists: whether the system can produce better, more game-native, commercially usable sites without sacrificing the strong V2.6.5 Core.
