## Inherited V2.6.5 production method


## Goal

Build a useful, fact-grounded, SEO-friendly, visually credible game wiki/site fast enough to capture the early search window of a newly released game, while preserving enough structure to scale into a durable wiki, database, guide site, or tool site.

A successful V1 is not only “technically correct.” It must also provide enough **topic coverage, navigation discoverability, player-facing usefulness, evidence-backed visual identity, route-level media lifecycle discipline, real game recognition, and screenshot-backed human visual quality** to compete with the best sites visible during the launch window.

## Core Strategy

**Public Data First → Resilient Evidence Verification → Discovery Research → Competitive Coverage → Structure First → Official Visual Evidence + Route Media Lifecycle → Launch Useful Coverage Fast → Game Recognition Review → Community Refine → Patch Maintain**

For very new games, keyword tools are often incomplete. Architecture should be derived from:

1. official public data;
2. Discovery Research;
3. competitor page-family coverage;
4. game entities and systems;
5. player journey and friction;
6. repeated community questions;
7. keyword validation;
8. Search Console feedback;
9. patch impact.

## Protected Methodology Boundaries

v2.6.3 preserves the v2.6.2 Stable Core and adds a bounded, provider-neutral monetization and ad-placement methodology without replacing the workflow.

Preserve:

- source/provenance discipline;
- the single runtime Page Inventory SSOT;
- Competitive Coverage, Minimum Wiki Coverage, Navigation Coverage, and Partial Page rules;
- player-facing UX boundaries;
- explicit deployment authorization and preview/production separation;
- KISS/YAGNI/80-20 fact-layer design;
- High Cohesion, Low Coupling, Modular, Adaptable, Stable Core / Flexible Edge;
- human approval gates;
- representative + risk-based QA;
- evidence discipline and no unnecessary abstraction.

Do not add:

- media or layout fields to the Page Inventory;
- media quotas;
- screenshot requirements for every route and viewport;
- automated legal scoring;
- image CDN/transcoding/video pipeline requirements;
- generic page/media/design DSLs.
- generalized transport engines;
- reviewer orchestration engines;
- media DAM/CMS/database requirements.

## Monetization / Ad Placement Contract

Monetization needs a placement and verification contract because technical integration alone does not prove a useful result:

```text
AD CODE EXISTS
!=
AD IS RENDERED
!=
AD IS VIEWABLE
```

A site may load provider code while monetization remains ineffective because placement, layout, provider delivery, or viewport visibility is poor. This contract defines methodology and review evidence only; exact formats, counts, dimensions, and positions remain project decisions. It is not a revenue-optimization guide.

Before implementation, decide whether monetization is `DISABLED`, `DEFERRED`, or `ENABLED`. A deferred decision records an owner or reason and keeps ad-specific output absent. Advertising configuration and placement do not belong in Runtime Page Inventory or the media lifecycle authority.

### Provider and Placement Responsibilities

These responsibilities must remain separate:

- **Provider responsibility** owns provider-specific script, configuration, bootstrap, markup, and public provider slot identity where applicable.
- **Placement responsibility** owns where an ad appears in page composition and its semantic relationship to surrounding content.

Pages or page-family composition should normally attach placements to stable semantic content anchors. Conceptual identifiers may include `home-primary`, `article-after-intro`, `article-mid-content`, or `before-footer`; these are examples, not a required universal enum, page-type policy engine, placement DSL, framework component, or pixel-offset contract.

### Hard Contracts

1. **Responsibility separation:** provider configuration/bootstrap/markup and semantic page placement must not be conflated.
2. **Literal disabled absence:** a disabled or unconfigured placement produces no ad-specific output.

   ```text
   disabled
   → no ad wrapper
   → no provider container
   → no reserved ad space
   → no provider request
   ```

   This is a framework outcome, not prescribed implementation syntax.
3. **Public/private boundary:** a public provider slot identifier may be client-visible when provider design requires it. Private API keys, admin tokens, account secrets, and credentials must never enter browser or other public output.
4. **Multiple-slot/key safety:** do not assume that one provider slot, key, container identity, or script instance may be duplicated across placements. The provider contract and project configuration must establish whether reuse is allowed, independent identity is required, and simultaneous instances are supported.
5. **Layout safety:** when creative dimensions are known or reasonably predictable, reserve appropriate responsive space to reduce layout shift without overlap or uncontrolled horizontal overflow. When dimensions are unknown, do not invent a large universal blank region.
6. **Evidence terminology:** `requested`, `rendered`, and `viewable` are separate claims; no earlier claim proves a later one.
7. **Capability distinction:** automation or reviewer-environment failure alone is not proof of ordinary-browser or production delivery failure.
8. **Diagnostic order:** verify DOM and layout layers before attributing an apparent region to an ad slot or provider.
9. **Conditional Human gate:** when monetization is enabled, production approval requires the lightweight Human Ads Review inside the existing Human Visual/Release methodology.

Ads must not obscure or hide core or SEO content, cause accidental `noindex`, block navigation, create severe layout breakage, create uncontrolled horizontal overflow, or unintentionally duplicate provider scripts.

### Soft Guidance

- A homepage primary monetization placement should normally attach to a stable content anchor and appear materially earlier than terminal/footer inventory.
- `before-footer` may be useful as supplemental inventory; it should not normally be the only primary homepage placement.
- Equivalent page types across locales should normally preserve the same semantic monetization intent. Language length and layout may change pixel offset or viewport depth, and documented locale-specific exceptions are allowed.
- Desktop and mobile should be reviewed in whole-page context for placement sense, obstruction, blank regions, and layout stability.
- Not every project, page type, page, or locale needs an ad. Exact ad count, format, dimensions, anchors, and positions remain project/provider decisions.

These points are guidance, not universal build rules or exact screen-depth thresholds.

### Requested / Rendered / Viewable

- **REQUESTED:** a provider request was initiated.
- **RENDERED:** actual creative or ad content was rendered into the page.
- **VIEWABLE:** the creative entered a meaningful viewport condition.

```text
requested
!=
rendered
!=
viewable
```

Record only the claim supported by the observed evidence and note the method or limitation where relevant. V2.6.3 defines no standard event API, analytics implementation, timer, or universal viewability threshold.

### Ad-Adjacent Layout Diagnostics

An ad-looking empty region is not proof that an ad slot exists:

```text
AN AD-LOOKING EMPTY REGION
!=
PROOF THAT AN AD SLOT EXISTS
```

Inspect in this order:

1. confirm the actual semantic ad-slot count;
2. inspect the provider container, instance identity, and actual child content;
3. inspect the semantic wrapper, visibility, reservation, and computed size;
4. inspect adjacent margin, padding, gap, min-height, aspect ratio, background, overflow, and pseudo-elements;
5. inspect the owning parent section/layout and neighboring content/footer relationship;
6. inspect provider request/response, account/domain/inventory state, browser extensions, automation, region/network, and ordinary-browser behavior.

Use these descriptive review classifications when evidence requires them:

- `PROVIDER/ENVIRONMENT CHECK REQUIRED` — provider delivery, inventory, account/domain, region, network, automation, or reviewer environment needs further verification.
- `HUMAN_BROWSER_CHECK_REQUIRED` — an ordinary logged-in or normal browser check is needed to settle a material provider-delivery claim.

For example, an automated browser may receive `403`, a provider may block automation, a reviewer environment may not reach the provider, inventory may be unavailable, or region/referrer behavior may differ. Preserve the evidence and classification. `AUTOMATION FAILURE != PRODUCTION DELIVERY FAILURE`. These classifications are handoff signals, not lifecycle states.

### Human Ads Review

Human Ads Review is a conditional checklist within the existing Human Visual/Release evidence. It is not a new phase, lifecycle table, persistent state, database, or ads state machine.

When applicable, inspect:

- whether placement is sensible in whole-page context;
- whether core content, SEO content, navigation, controls, or footer are obstructed;
- whether desktop and mobile layout are acceptable;
- whether any blank or dark ad-sized region has an explained owner;
- whether known-format reservation is reasonable and layout shift risk is controlled;
- whether an ordinary browser can render provider creative when provider verification matters;
- whether `requested`, `rendered`, and `viewable` evidence is recorded separately without overclaiming;
- whether equivalent locale pages preserve semantic placement intent, allowing different absolute depth;
- whether ad count and slot/key/script multiplicity match the approved provider/project contract;
- whether public output avoids private credentials and internal workflow language;
- whether there is any obvious SEO or UX regression.

Record the checklist evidence and outcome in the existing Human Visual Review / Human Release artifacts. If provider availability remains inconclusive while structure and layout pass, retain the applicable provider/environment or Human-browser classification; do not convert uncertainty into either approval or a deterministic build failure.

### Non-Goals

V2.6.3 does not introduce a provider registry, multi-provider orchestration, provider plugin framework, analytics backend, dashboard, database, A/B testing, automatic optimization, automatic provider switching, bid management, provider account management, provider API integration, provider-specific framework, page-type policy engine, ad DSL, hardcoded screen-depth threshold, mandatory second slot, new ads lifecycle state machine, or standard runtime observability API.

The SOP does not specify Astro component filenames, TypeScript interfaces, Starter file structure, prop names, CSS implementation, provider script code, or analytics hooks. Those are Starter or project implementation concerns.

## Verification Transport Resilience Policy

Verification must be evidence-based, not transport-dependent.

Separate:

```text
evidence validity
from
transport availability
```

Required flow:

```text
Preferred read-only transport
→ classify transport/auth/session failure
→ approved read-only fallback
→ preserve primary failure evidence
→ preserve source/provenance identity
→ verify equivalent evidence
→ continue if evidence verifies
```

Access states:

```text
READ
PARTIAL
UNAVAILABLE
TRANSPORT_BLOCKED
AUTH_BLOCKED
```

Provenance checks may additionally record:

```text
PRIMARY_TRANSPORT_FAILED
FALLBACK_VERIFIED
```

Use this for Git provenance verification, official source reading, and required evidence retrieval.

BLOCK only when required evidence itself cannot be verified. Do not BLOCK merely because one preferred tool, reader, session, or API failed.

Approved fallback must remain read-only, preserve the same source/provenance identity, and verify equivalent evidence. Do not silently downgrade official evidence to lower-authority evidence, bypass anti-bot systems, solve CAPTCHA, export cookies, or perform write actions.

This is a methodology rule, not a generalized transport engine.

## Reviewer Capability Preflight

Before evidence-dependent independent review, establish whether the reviewer can access enough evidence to perform the review.

Evidence classes include:

- upstream Git refs / provenance;
- project status artifacts;
- execution summaries;
- build/test evidence;
- route/reconciliation evidence;
- source evidence;
- visual evidence when applicable.

Independent review does not require the same tool or same transport. It requires independent access to sufficient evidence.

If the reviewer cannot access required evidence because of reviewer/tool/session limitations, classify:

```text
REVIEWER CAPABILITY BLOCKED
```

Do not label:

```text
PROJECT BLOCKED
```

unless the project evidence itself is defective or cannot be verified through approved evidence channels.

If evidence can be safely exposed through an approved read-only channel, expose it, rerun review, and preserve the failed review attempt in process history. Never send credentials, tokens, cookies, or secret-bearing logs to satisfy review.

# Step 9 — Competitive Coverage Gate

This is a **blocking planning gate**.

For each meaningful page family observed from competitors, game entities, player journey, and discovery, assign one decision:

```text
COVER_NOW
COVER_PARTIAL
DEFER
NOT_RELEVANT
```

For `DEFER`, document:

- why;
- whether competitors already cover it;
- whether user/search intent is visible;
- whether a partial page could satisfy the intent safely;
- what evidence/data is missing;
- the SEO/UX cost of delaying;
- human approval status if the gap is material.

Do not allow “data incomplete” as the only reason to omit a high-value family.

# Partial Page Rule

**Incomplete evidence does not automatically mean the page cannot exist.**

Separate:

```text
Page existence
from
Claim completeness
```

Examples:

- Skill Tree system verified, nodes incomplete → publish system/strategy overview; defer node database.
- Gear system verified, catalog incomplete → publish gear-system guide; defer full item database.
- Worlds verified, detailed drops incomplete → publish world/progression overview; defer unsupported drop tables.

A partial page must:

- answer a real intent;
- clearly limit itself to verified information;
- avoid fake completeness;
- state unknowns when useful;
- not masquerade as a complete database.

## Starter Readiness Projection Boundary

The SOP owns the full media lifecycle methodology, allowed fields/states, project artifact expectations, and Human/rights/visual decision semantics.

Starter may read the media decision table, validate its structure, resolve rows against the Runtime Page Inventory, project lifecycle rows into a narrow readiness state, and report deterministic readiness evidence.

Starter must not:

- own rights decisions;
- validate whether a Human waiver or reclassification is substantively correct;
- decide visual quality;
- become publication authority;
- add lifecycle fields to Runtime Page Inventory;
- invent lifecycle meanings.

Starter lifecycle-to-readiness mapping must be explicit, documented, SOP-derived, exact-state-combination based, and ordered by precedence. Unknown or unsupported lifecycle states are malformed input and must fail closed; they must not be guessed through substring matching, synonym matching, state labels outside the allowed list, or free-text interpretation.

Legal lifecycle states are only:

- media need: `HIGH PRIORITY`, `RECOMMENDED`, `OPTIONAL`, `NO MEDIA NEEDED`;
- candidate: `NOT FOUND`, `FOUND`, `SEMANTICALLY VERIFIED`;
- rights: `VERIFIED`, `UNRESOLVED`, `HUMAN RISK ACCEPTED`, `NOT REQUIRED FOR EMBED`;
- human decision: `APPROVED`, `WAIVED`, `REVISE`, `BLOCK`, `PENDING`;
- integration: `NOT INTEGRATED`, `INTEGRATED`, `FALLBACK ONLY`;
- visual gate: `PENDING`, `PASS`, `REVISE`, `BLOCK`.

Readiness projection decision order:

1. Validate exact enum values against the allowed lifecycle states.
2. Resolve `pageId_or_route` to exactly one Runtime Page Inventory row.
3. Branch first on `media_need`.
4. Apply the ordered state-combination rules for that branch.
5. Produce narrow readiness evidence. Starter must not infer undocumented combinations.

Within a branch, evaluate rows in order. The first matching rule is the single projection outcome. Later rules are not evaluated for that row.

`NO MEDIA NEEDED` branch:

| Precedence | Exact state combination | Narrow readiness projection |
|---|---|---|
| 1 - conflict/revise/block | `rights_state: UNRESOLVED`, `human_decision: REVISE` or `BLOCK`, or `visual_gate_state: REVISE` or `BLOCK` | No-media conflict evidence. Conflict is not downgraded to pending. No-media cannot hide unresolved rights, failed sourcing, unfinished integration, or deferred visual work. |
| 2 - pending Human/visual review | `human_decision: PENDING` or `visual_gate_state: PENDING` | Pending no-media review evidence. Do not classify unresolved merely because `candidate_state: NOT FOUND` or `integration_state: NOT INTEGRATED`. |
| 3 - resolved no-media | non-empty positive `need_rationale`; `candidate_state: NOT FOUND`; `rights_state: NOT REQUIRED FOR EMBED`; `human_decision: APPROVED` or `WAIVED`; `integration_state: NOT INTEGRATED`; `visual_gate_state: PASS` | `priority: NO MEDIA NEEDED`; resolved no-media readiness. `NOT FOUND` and `NOT INTEGRATED` are no-media-compatible in this branch only. |
| 4 - unsupported | any other exact-state combination | Unsupported/malformed lifecycle combination. |

`HIGH PRIORITY`, `RECOMMENDED`, and `OPTIONAL` branch:

| Precedence | Exact state combination | Narrow readiness projection |
|---|---|---|
| 1 - explicit Human/visual revise/block | `human_decision: REVISE` or `BLOCK`, or `visual_gate_state: REVISE` or `BLOCK` | Blocking readiness evidence. |
| 2 - Human-approved waiver/reclassification | `human_decision: WAIVED`; `visual_gate_state: PASS`; `candidate_state: NOT FOUND` or `FOUND` or `SEMANTICALLY VERIFIED`; `rights_state: VERIFIED` or `UNRESOLVED` or `HUMAN RISK ACCEPTED` or `NOT REQUIRED FOR EMBED`; `integration_state: NOT INTEGRATED` or `INTEGRATED` or `FALLBACK ONLY`; non-empty `notes` or `owner_or_defer_reason` explaining waiver/reclassification/debt | Resolved by Human-owned waiver/reclassification evidence. Starter validates the exact allowed combination and recorded explanation; it does not judge whether the Human decision is substantively valid. |
| 3 - normal approved integrated media | `candidate_state: SEMANTICALLY VERIFIED`; `rights_state: VERIFIED` or `HUMAN RISK ACCEPTED` or `NOT REQUIRED FOR EMBED`; `human_decision: APPROVED`; `integration_state: INTEGRATED`; `visual_gate_state: PASS` | Resolved integrated-media readiness. `HIGH PRIORITY` maps to `priority: HIGH PRIORITY`; `RECOMMENDED` and `OPTIONAL` remain non-blocking readiness categories. |
| 4 - pending media review | `human_decision: PENDING` or `visual_gate_state: PENDING` | Pending media readiness evidence. Severity follows `media_need`. |
| 5 - fallback-only without waiver | `integration_state: FALLBACK ONLY` | Fallback-only readiness evidence. `FALLBACK ONLY` is not automatically resolved; severity follows `media_need`. |
| 6 - unsupported | any other exact-state combination | Unsupported/malformed lifecycle combination. |

Combinations not matched by exactly one ordered rule are unsupported for Starter projection and must fail closed as malformed input until the SOP/project records a supported exact combination.

Human waiver or reclassification may alter the methodology outcome only when represented by SOP-owned legal states. Starter may report the exact state combination; it must not determine whether the Human decision is substantively valid.

## pageId_or_route Identity Resolution

`pageId_or_route` identifies a media row only by resolving against the Runtime Page Inventory.

Resolution requirements:

- exactly one valid match to an existing Page Inventory `pageId` or `route` is required;
- zero matches are a validation error;
- ambiguous or multiple matches are a validation error;
- the media table cannot create new page identities;
- Runtime Page Inventory remains the publication SSOT;
- a leading `/` may be used only as a parsing hint for route-like values, not as route authority by itself.

`NO MEDIA NEEDED` means:

```text
the page remains useful,
comprehensible,
and visually complete without media
```

It must not mean:

```text
rights unresolved
candidate missing
integration unfinished
visual work deferred
we did not find media
→ therefore no media needed
```

Rights status and media need are separate decisions.

If homepage media is `HIGH PRIORITY` but remains unresolved by Human Visual Review, the minimum outcome is `REVISE` unless Human explicitly approves a no-media exception.

## WS03A semantic visual-role choice

The candidate Starter supports a bounded site-wide `visualRoles` choice, not a
Theme Engine. The four supported roles are font (`editorial`/`interface`), density
(`comfortable`/`compact`), shape (`square`/`soft`) and decorative state
(`lifted`/`quiet`). A project owner records visual evidence and an explicit
four-role decision; Starter implements it, execution tools verify it, and later
human visual review assesses actual game identity and fidelity.

Legacy omission resolves to `editorial / comfortable / square / lifted` with the
previous font stacks, responsive geometry, square surfaces and hover treatments.
It remains an unconfigured fallback, not a project-approved theme. Once authored,
all four values are required; unsupported roles, arbitrary fonts/CSS/units,
component overrides and genre/name/logo inference are rejected. Palette authority
stays in `theme.css`; Inventory module alone owns page-family accent mapping.

The resolver returns identifiers only. HTML data attributes select semantic CSS
tokens; no route, page type or component invents a role. Compact preserves44px
control minima; quiet changes only nonessential hover lift/shadow. Focus/current,
open/closed, navigation/keyboard and reduced-motion safeguards stay Stable Core.
No font provider, media/share/search/freshness capability is added by this slice.

Require schema positive/negative examples, exact legacy fallback checks, actual
alternate-profile final output and three-engine computed-style/hover evidence,
then new-source root/adoption checks, unchanged fresh47, residual/counterpart
and normal cleanup audits, and independent continuation review. This technical
interface supplies no automatic GI/VF/AX/PA outcome or formal WS03 closure.
Iteration22 readiness was accepted for03Aonly; the first03A mutation makes it
STALE and requires the per-slice new-source continuation path described above.
