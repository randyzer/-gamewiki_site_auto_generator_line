# Acceptance checklist

## Input and provenance

- [ ] Game name and workspace were explicit.
- [ ] All upstream inputs resolved uniquely.
- [ ] Template copy manifest destination matches the workspace.
- [ ] Git baseline was recorded and approved when dirty.
- [ ] Original template library remained unchanged.

## Global identity

- [ ] Header, footer, navigation, sidebar, About, legal pages, 404, metadata, and manifest use the target identity.
- [ ] Official links are verified upstream links.
- [ ] No fake contact, operator, community, metric, or live-status claim.
- [ ] Demo names/domains/entities are absent from public implementation.
- [ ] Provenance documents are allowlisted during residue scanning.

## Homepage

- [ ] Homepage claims are supported by the homepage research.
- [ ] Homepage modules were mapped by purpose.
- [ ] Codes are verified or honestly reported as unconfirmed/unavailable.
- [ ] HSL theme values are centralized.
- [ ] Recommended languages are not misrepresented as implemented.
- [ ] Misleading demo media was replaced, removed, or neutralized.

## Icons

- [ ] ZIP integrity passed.
- [ ] Expected members were extracted safely.
- [ ] Framework metadata references valid paths.
- [ ] Original ZIP remains in the resolved research root.
- [ ] Icon is not described as an official logo.

## Inner pages

- [ ] Every keyword has one manifest outcome.
- [ ] Every published page is supported by its material file.
- [ ] PARTIAL and BLOCKED decisions are justified.
- [ ] Draft/blocked pages are excluded from public discovery.
- [ ] Titles and descriptions meet constraints or document a justified exception.
- [ ] Openings answer search intent directly.
- [ ] No padding, copied transcript prose, invented entity, number, code, or mechanism.
- [ ] Related links point only to published relevant pages.
- [ ] Version-sensitive facts include verification context.

## Technical validation

- [ ] typecheck result recorded when script exists.
- [ ] lint result recorded when script exists.
- [ ] test result recorded when script exists.
- [ ] build result recorded when script exists.
- [ ] Internal links and public routes checked.
- [ ] Favicon and manifest paths checked.
- [ ] Mobile/overflow checks run when the template provides them.
- [ ] No unauthorized dependency added.
- [ ] No test or validation rule weakened.

## Completion

COMPLETED requires every applicable item above to pass. PARTIAL is required when useful integration exists but one or more non-destructive blockers remain. BLOCKED applies when inputs, evidence, project integrity, or validation prevents a reliable implementation.
