# Agent 个人使用版架构与执行计划

状态：当前主线。目标是帮助单一操作者高效完成真实游戏攻略站，不以企业级多租户或敌对宿主为设计前提。

## 1. 核心目标

给定游戏身份、原始关键词和站点目录，Agent 按顺序完成七个阶段，保存每一步的证据和产物，失败后从已验证的检查点恢复，最终生成可人工审查的部署计划。真实部署仍需单独批准。

成功必须同时满足：

1. 真实 Skill 和真实工具能够执行，不能用测试替身代替运行结论。
2. `PARTIAL`、`BLOCKED` 和外部服务限制必须如实保留。
3. 已完成阶段不重复执行，恢复数据经过哈希复验。
4. 第 7 阶段先停在部署计划；计划摘要未获批准前不执行部署。

## 2. 信任边界

本架构信任本机操作者、宿主进程、当前 Git 仓库和已经配置的 Skill 清单。Worker 输出、网络内容和恢复文件在宿主验证前均不可信。

因此主线保留产物验证、路径边界、Skill 锁、检查点、恢复哈希、精确批准和部署门禁。Code Authority、签名密钥、审批事件链、抗回滚权威和多租户隔离不属于个人版交付前置条件。

## 3. 架构组成

| 层 | 现有实现 | 职责 |
| --- | --- | --- |
| 输入与启动 | `cli.mjs`、`terminal-run.mjs` | 校验输入，生成预览和确认快照，启动或恢复一次运行 |
| 七阶段编排 | `pipeline.mjs`、`stages.mjs` | 决定阶段顺序、依赖、状态和重试失效范围 |
| 真实执行 | `skill-executor.mjs` | 按阶段权限调用已锁定 Skill 和宿主工具 |
| 产物验收 | `artifact-validator.mjs` 及阶段专用验证器 | 只接受路径、身份和内容都满足要求的产物 |
| 恢复与交接 | `keyword-recovery.mjs`、`research-handoff.mjs` | 保存不可变恢复快照；把不完整研究安全交给后续阶段 |
| 发布约束 | `route-publication.mjs` | 完成内容可发布；部分内容只作草稿且 noindex；阻塞内容不生成路由 |
| 部署门禁 | `deployment-plan.mjs` 及 Pipeline | 先生成计划，再以精确摘要取得单独执行批准 |

Agent 不再新增第二套 runner。现有 V1 Pipeline 就是个人版真实执行主线；V2 中已经稳定的解析或验证能力可以被复用，但不要求先完成整套 V2 信任基础设施。

## 4. 七阶段业务流程

| 阶段 | 功能 | 通过条件 |
| --- | --- | --- |
| 1 首页调研与图标 | 获取首页资料、生成并验证图标 | 首页材料和图标包通过真实验证 |
| 2 关键词资料调研 | 分类关键词并收集逐词证据 | 完整研究通过，或生成可审查的部分研究交接 |
| 3 模板选择 | 选择并复制固定模板 | 模板报告、复制清单和残留扫描通过 |
| 4 内容整合 | 把已验证资料写入站点 | 页面清单、来源、缺口和构建结果通过 |
| 5 UI/UX 审计 | 宿主预览并检查主要页面 | 审计报告、结构化结果和修改计划通过 |
| 6 上线前验收 | 检查路由、内容、SEO 和构建 | 验收结论允许进入部署计划，或明确阻塞项 |
| 7 部署计划 | 生成操作、文件、风险和回滚计划 | 计划可审查并停在人工批准门前 |

## 5. 关键词研究的安全语义

每份关键词素材分开记录三个状态：

- `declaredStatus`：Skill 原文声明的状态。
- `contractStatus`：原文是否满足锁定契约。
- `status`：后续阶段使用的安全状态。

处理规则：

| 原始情况 | 后续状态 | 路由策略 |
| --- | --- | --- |
| `COMPLETED` 且契约有效、无缺口 | `COMPLETED` | `PUBLISH` |
| `COMPLETED` 但仍有有效“待确认”项 | `PARTIAL`，同时保留 `INVALID` 诊断 | `DRAFT_ONLY` |
| `PARTIAL` 且有明确缺口 | `PARTIAL` | `DRAFT_ONLY` |
| `BLOCKED` 且有明确缺口 | `BLOCKED` | `OMIT` |
| 格式损坏、关键词不匹配或缺少必要状态 | 拒绝创建交接 | 不推进 |

候选交接文件绑定恢复快照、素材状态、待确认原始行、站点版本和域名。只有完全匹配候选摘要的人工批准才能让 `PARTIAL` 阶段继续；该批准不会把研究改成 `PASSED`，也不会把草稿变成可索引页面。

## 6. 防偏航机制

后续开发必须执行以下门禁，不再依赖操作者发现偏离后纠正：

1. **目标门禁**：每项变更必须直接解决当前真实建站阻塞，或是该修复不可缺少的验证；无法对应时不进入主线。
2. **范围门禁**：每个工作包在编码前冻结文件、功能和验收标准；超出范围先停止，并重做计划审查，不能顺手扩建。
3. **真实验收门禁**：单元测试只证明代码行为，真实阶段运行才证明 Agent 可用；未到部署计划不得宣称整个 Agent 已完成。
4. **复杂度门禁**：个人版默认信任本机操作者和宿主。签名、抗回滚、多租户和新的平行执行框架只有出现已证明的真实需求才可立项。
5. **故障分类门禁**：先区分 Agent 缺陷、内容证据不足和外部服务限制；只修 Agent 缺陷，不能用架构代码掩盖 429、403、登录或第一手资料缺失。
6. **合并门禁**：每个 PR 必须列出对应路线图阶段、准确文件、测试、风险和回滚；ChatGPT 审查准确 Head 后才可合并。
7. **进度门禁**：每完成一个工作包即更新路线图的“已完成/下一步/未完成”，不允许同时推进多个未验收工作包。

任何新建议先回答一个问题：它能否让当前真实游戏站更快、更可靠地进入下一阶段？答案不明确时，不实施。

## 7. 当前开发计划

| 工作包 | 预计上限 | 输出 | 完成标准 |
| --- | ---: | --- | --- |
| A 架构冻结 | 30 分钟 | 本文、当前路线图、README | 个人版边界和七阶段口径经复审 |
| B 阶段 2 兼容修复 | 60 分钟 | handoff 解析与回归测试 | 31 份 attempt 10 fixture 得到 27 `PARTIAL`、4 `BLOCKED`，没有可发布页 |
| C 全量回归与独立审查 | 60 分钟 | 全量测试、PR、审查记录 | 测试全绿，历史 002 哈希不变，PR 获批后合并 |
| D 真实 002 验证 | 90 分钟 | 从恢复快照继续到部署计划 | 保留服务暂停决定，完成能完成的阶段；外部阻塞如实报告，不部署 |

四小时是交付上限，不是增加功能的预算。若工作包 D 遇到登录、验证码、平台限流或第三方服务不可用，只修复可证明的 Agent 缺陷；外部限制保留为明确阻塞，不继续扩建架构。

## 8. 验收与停止条件

Agent 开发完成需满足：

1. 相关单元与 Pipeline 回归、V2 兼容测试和全量测试通过。
2. Wallpaper Engine attempt 10 格式能生成不可变研究交接候选。
3. 未批准时阶段 3 不启动；精确批准后只允许草稿和遗漏策略进入后续阶段。
4. 历史 `agent/runs/wallpaper-engine-002/` 字节不因代码测试而改变。
5. 真实验证到达可审查部署计划，或留下一个可由操作者采取行动的外部阻塞；`deploymentExecuted=false`。

出现以下情况立即停止扩大范围：需要改 Skill、自动批准部分研究、把不完整内容标成可发布、绕过暂停服务、修改历史恢复快照、执行部署，或需要修改本计划之外的核心架构。
