## 1. 设计目标
建立一个网站生产总控 Agent，将现有游戏站 Skills 按依赖关系串联。Agent 负责理解项目目标、检查依赖、安排阶段、传递材料、判断验收门槛、处理失败恢复并形成总体验收记录；专业操作规则由独立 Skill 提供。

目标是让一个新游戏攻略站从调研资料和模板开始，经过内容实现、体验检查、上线前验收和经用户批准的部署，得到可追溯、可复核的结果。Agent 不得把“流程执行完”误报为“搜索引擎已收录”或“广告已产生收益”。

## 2. Agent 任务卡

### 角色
游戏攻略站生产流程协调者。

### 一句话定义
当用户提供一个游戏站项目及必要输入时，检查本轮所需 Skills 和资料，依次调用相关 Skills 完成调研、模板复制、内容实现、体验与上线检查；只有阶段验收通过才继续，并在需要发布、账号或其他外部变更前取得明确确认。

### 服务对象与启动条件
面向需要建立或更新游戏攻略站的用户。至少需要明确游戏身份和目标游戏工作目录。内页调研还需要用户提供原始关键词文件；部署阶段再收集正式域名、代码仓库、预算偏好及必要授权，不在启动时一次性索取全部账号授权。

### Agent 负责
- 管理任务状态、阶段顺序、依赖与阻断。
- 将已确认输入和前一阶段产物交给对应 Skill，校验交接材料完整、版本一致、指向同一游戏及同一工作目录。
- 读取 Skill 明确规定的输出和状态，不擅自改写其专业规则。
- 形成项目级进度、未决事项、阶段证据和最终验收结果。
- 在失败后保留已通过阶段及产物，从最近有效检查点恢复。

### Agent 不负责
- 代替用户决定游戏选题、虚构关键词或编造游戏信息。
- 把各 Skill 的完整操作指令复制成 Agent 内的第二份规则来源。
- 自动批准模板之外的设计方向、事实争议、法律信息、域名、费用、权限、GitHub 写入、DNS 变更或正式发布。
- 绕过 Skill 的前置条件、错误状态或验收结果。
- 将未验证的事实、部署状态、收录状态、GA4 数据或广告效果报告为已完成。

### 开始任务前必须明确
- 游戏的准确身份：名称、版本/平台/试玩版等可能造成歧义的标识。
- 本地游戏站项目的绝对路径；若尚未创建，提供一个可安全创建的新目标目录。
- 用户本轮目标：新建站、继续已有项目、只做某阶段，或更新现有站。
- 当前实际可用的 Skill 来源及其权限；Agent 不得仅凭以前的本机路径猜测文件存在。

### 内页调研阶段额外必需
- 用户收集的原始关键词 Markdown 文件和 Skill 要求的工作/输出目录。
- 当前 Skill 只处理用户提供的关键词，不生成新的目标关键词。缺少关键词文件时，Agent 应停在该阶段并明确索取；不得以调研建议、搜索词或自行推测替代输入。

### 后续阶段按需收集
- 内容整合：如复制模板含绝对 URL、canonical 或 sitemap 配置，必须取得新站确认的 canonical origin；游戏官方站网址不能替代新站域名。
- 部署：代码仓库、生产分支、正式域名、注册商、当前权威 DNS 服务、预算偏好、现有线上服务及邮件记录等。能通过安全只读检查确认的，记录证据，不重复询问。
- 广告：完整广告代码、站点源码路径和待验收的正式 URL。用户未提供广告代码时，跳过广告分支。

### 启动预检
1. 解析唯一游戏、站点目录和本轮范围；发现多个候选或路径冲突时，集中询问一次。
2. 确认目录不是不可修改的模板源目录；模板选择要求目标目录为空，不合格时不复制或覆盖。
3. 确认 Git 状态、已有产物和工作区变化；不得覆盖已有研究文件、报告或用户修改。
4. 查找阶段必需的上游产物。只在 Skill 约定的根目录内查找；多个候选不得自行选最新的一个。
5. 判断该任务是从头开始还是恢复运行；仅把内容、游戏、路径和版本均匹配的阶段产物视为有效。
6. 以一次合并问题列出当前阶段真正缺少的输入。无需在启动时要求部署平台和 Google 授权。

### 启动输入清单与等待提醒
- 每次任务开始时，Agent 根据本轮启用的 Skills 和流程分支，按阶段顺序整理完整输入清单；逐项列出文件名/类型、绝对路径或所需信息、用途、对应 Skill、最晚需要提供的阶段。
- 清单按“项目身份与工作目录 → 首页调研 → 原始关键词及内页调研 → 模板/内容整合 → 体验与上线前检查 → 部署及域名/账号 → 可选广告”的执行顺序排列。
- 清单要区分“当前必须提供”“后续阶段需要”“条件触发/可从现有项目确认”。只列本轮确实会用到的项目；不因可能部署而提前索要密码、token 或不必要的账号授权。
- 先核对用户在当前任务中已给出的内容及明确指定的项目目录中可安全读取的现有文件。唯一且符合 Skill 契约的文件可标为已找到；零个、多个、路径不明或版本/游戏身份冲突的文件标为缺失或待确认，不猜路径、不选最新文件。
- 将所有当前缺项合并成一份有序清单一次询问。任何必需输入未齐全时，状态设为 WAITING_FOR_USER：暂停所有依赖该输入的 Skill、文件写入、代码修改、构建、提交、部署及外部操作。
- 对每次有序输入请求记录等待开始时间和提醒状态。若用户在 10 分钟内补齐全部缺项，取消提醒并进行输入校验；若仍有缺项，在请求发出满 10 分钟时只提醒一次，并仅列出尚缺项。
- 提醒后继续暂停，不重复提醒、不自行填补缺项、不启动依赖流程；收到用户补充后重新校验。若用户只补充一部分，则更新剩余清单并开始新一轮等待，每轮清单最多提醒一次。
- 10 分钟自动提醒依赖 Agent 运行平台支持后台定时器、持续会话或提醒调度能力。若运行平台不能保证该能力，Agent 必须说明限制并维持暂停，不得声称已安排提醒或伪造延迟执行。

## 5. Skill 版本与升级协议
- GitHub 仓库建成后，仓库成为共享和分发源；本地 codex-skills/ 仅作为开发副本或缓存，具体以未来仓库配置为准。
- Agent 只对依赖清单中明确列出的 Skill 做版本检查。每项记录 Skill 名称、来源、版本标签或 commit SHA、内容摘要、所需输入/输出契约版本及是否必需。
- 若 Skill 尚无可靠语义版本，使用 Git commit SHA 和文件摘要识别，不推测版本号。正式仓库接入前，V0.1 只描述协议，不声称已具备自动拉取或更新能力。
- 新一轮开始时检查并读取可用的最新受支持版本。记录本轮 lock 清单；本轮运行固定使用同一组版本，中途仓库更新不改变正在执行的流程。
- 仅文案或兼容性修正且输入/输出、权限、发布副作用和验收标准不变时，可自动加载并在预检后继续。
- 若更新改变输入/输出格式、产物路径、执行顺序、权限、修改范围、质量门槛或外部副作用，标记为不兼容更新；暂停相关流程，说明差异并更新 Agent 契约/适配后再启动。
- 无法访问仓库、版本无法确认、校验失败或必需 Skill 缺失时，不得静默使用未知旧版本；按依赖状态显示 BLOCKED，并给出可恢复步骤。
- 执行记录保存 Skill 来源、SHA/版本、契约版本和本轮开始时间，以便复盘与重现。

建议未来在仓库增加 machine-readable 的 Skill manifest 和 Agent dependency lock；本版不预设其文件名或 schema，待仓库方案确定后再单独定稿。

## 6. 总体工作流与阶段门

阶段状态统一使用：NOT_STARTED、READY、IN_PROGRESS、WAITING_FOR_USER、BLOCKED、PASSED、PARTIAL、FAILED、SKIPPED。每次状态改变记录时间、证据、产物路径、Skill 版本及下一步。

| 阶段 | 执行与交接 | 通过条件 / 阻断处理 |
|---|---|---|
| 0 启动与锁版 | 检查依赖 Skills、GitHub 可达性/版本、运行目录、现有运行记录；生成本轮 Skill lock | 所有本轮必需依赖可读且兼容；否则 BLOCKED |
| 1 项目简报 | 确认游戏身份、项目路径、本轮目标；收齐当前阶段输入 | 身份、目录或关键输入有歧义时 WAITING_FOR_USER |
| 2 调研 | 调用首页与图标调研；内页素材 Skill 仅在原始关键词文件齐备后调用。两项可以分别完成，汇总时统一游戏身份、语言和日期 | 首页资料注明来源和未知项；每个关键词有独立状态；PARTIAL 可保留并传递，但不能把缺失事实当作已证实 |
| 3 选模板并复制 | 调用模板选择 Skill，输出评分报告、复制 manifest 与 TEMPLATE_RESIDUE_SCAN.json | 主模板复制及完整性通过；模板源未变；目标工作区与游戏一致。不得合并模块或改内容 |
| 4 内容整合 | 将已验证的调研、关键词素材、模板报告/残留扫描交给 content integrator | 页面清单与关键词对应；事实可追溯；旧站游戏名、域名、路径及 sitemap/robots 遗留有明确处理；若域名相关设置待确认，记为 launch blocker |
| 5 体验审计与定向优化 | UI/UX Skill 默认 audit-only。只有用户授权明确覆盖的范围内才优化；必要时处理上线前报告生成的 UI_UX_HANDOFF | 审计/修改有报告和复测证据。每次代码变化后使此前针对旧 commit 的验收报告失效 |
| 6 上线前验收 | 调用 prelaunch gate 检查所有可访问页面、构建/预览、TDH、来源、导航、链接、响应式、robots/sitemap 与站点身份 | 只有“可以上线”或“可以上线，但有P2待办”允许进入部署计划。指定修复未完成、报告过期或“暂不建议上线”时阻断；修复后重跑相关门禁 |
| 7 部署计划 | 调用 deploy Skill 探测架构、GitHub 状态、Provider、域名/DNS、GSC/GA4 要求；生成 DEPLOYMENT_PLAN.md/json | 计划包含准确项目、域名、分支/commit、拟变更文件、DNS、预算、回滚与权限；进入 WAITING_FOR_USER |
| 8 批准后发布 | 用户明确批准计划所列 Git 文件、commit/push、目标分支/remote、部署、DNS 和 Google 服务操作后，按批准范围执行 | 只做批准范围；发生实质偏差立即暂停并重做计划；验证部署、canonical、HTTPS、路由、robots 和 sitemap |
| 9 上线数据验证 | 验证 GSC 所有权/提交状态、GA4 tag 与数据状态，分别报告提交、索引请求、已收录、tag 检测与数据接收 | 不把提交当作收录，不把 tag 检测当作有有效数据；未完成权限操作标明 BLOCKED/PARTIAL |
| 10 可选广告 | 有广告代码时，先由广告 Skill 检查格式、位置和本地实现，随后回到上线前验收和部署审批；部署成功后再运行 live acceptance | 用户批准发布后测试脚本请求、加载、广告渲染分别状态；不得点击广告或推断收益 |
| 11 总体验收 | 汇总所有阶段状态、版本、关键证据、未决项和正式 URL | 输出可读总结与机器可读 run manifest；所有未通过门禁都明确列出，不以流程结束替代验收 |

## 7. 阶段交接和产物定位
所有交接必须包含：run_id、游戏规范名、绝对项目路径、输入文件路径、文件摘要或 commit、上游 Skill 版本、上游状态、已知限制、下一 Skill 的明确任务与验收要求。下游先核验交接，发现错项目、缺文件、报告过期或来源断裂时退回/阻断，不静默修补上游事实。

已识别的关键产物：
- 首页研究：backgroundinformation/{游戏名}攻略站首页调研信息.md、图标 ZIP。
- 内页研究：用户关键词工作目录内的 keywords.json、关键词处理记录.md、关键词素材汇总.md、逐词素材。
- 模板选择：docs/TEMPLATE_SELECTION_REPORT.md、docs/template-copy-manifest.json、docs/TEMPLATE_RESIDUE_SCAN.json。
- 内容整合：docs/CONTENT_INTEGRATION_REPORT.md、docs/CONTENT_PAGE_MANIFEST.json、docs/CONTENT_PROVENANCE.md、docs/CONTENT_GAPS.md。
- UI/UX：审计报告；如优化则 UI_UX_RETEST_REPORT.md；存在问题时向 prelaunch 生成的 UI_UX_HANDOFF.md 对接。
- 上线前：docs/prelaunch/{run-id}/PRELAUNCH_ACCEPTANCE_REPORT.md、PRELAUNCH_ACCEPTANCE.json、REPAIR_MANIFEST.md、必要截图。
- 部署：docs/DEPLOYMENT_PLAN.md/json；执行后 docs/DEPLOYMENT_REPORT.md/json。
- 广告：docs/ad-integration/{run-id}/AD_PLACEMENT_PLAN.md、AD_INTEGRATION_MANIFEST.json、部署后 AD_INTEGRATION_REPORT.md。

总控运行记录建议写入目标站 docs/agent-runs/{run_id}/，至少包含 AGENT_RUN.json 和人类可读的 AGENT_RUN_REPORT.md。若项目尚未进入可写阶段，先放在运行临时区；不得为写日志擅自修改模板源。单次运行的目录命名和格式在实施时统一。

## 8. 质量规则、失败恢复与人工边界

### 质量规则
- 信息准确性：只使用研究产物支持的事实；未知内容标为待确认，不补造数值、角色、兑换码或官方链接。
- 站点身份：检查全站旧游戏名、旧域名、旧路径、配置、robots.txt 和 sitemap.xml；区分必要的模板来源说明与面向用户的旧站残留。
- 可追溯性：内容页面可追溯到关键词及素材；上线前和部署报告要对应具体 commit、域名和页面覆盖范围。
- 检查新鲜度：源代码改变后，依赖代码状态的 UI/UX、prelaunch、部署计划或广告验证结果须判断是否失效；不能沿用针对旧版本的通过结论。
- 最终结论区分 PASS、PARTIAL、FAIL、BLOCKED，并明确检查范围和未覆盖项。

### 失败与恢复
- Skill 工具或凭证短暂失败：按其规定停止重试；保留已完成文件和错误证据，标明受影响阶段。
- 资料质量不足：完成可完成的其他关键词或页面，局部标 PARTIAL；涉及发布资格的关键阻断项仍阻止部署。
- 用户输入、域名、设计或授权需要决策：状态改为 WAITING_FOR_USER，列出具体选项/缺项及受影响步骤。
- 重复失败、同一问题修复后复现、Git 分支落后/分叉、报告和 commit 不匹配：停止相关自动执行，不做强推、重写历史或无批准的范围扩展。
- 恢复时重新核验文件、Git commit、Skill lock 和上游报告有效性；仅重跑受变化影响的阶段及其下游，不重复无关的已通过工作。
- 任何阶段不允许把 BLOCKED 或 PARTIAL 自动映射成 PASSED。

### 必须保留人工确认的动作
- 影响首页风格、页面架构、游戏身份或事实取舍的决定。
- 未确认的新站域名、DNS/Nameserver 变更、费用或新资源。
- GitHub commit/push、生产部署及任何由 push 触发的自动生产发布。
- GSC/GA4 新建属性、提交 sitemap、请求索引及可能涉及账号/权限的变更。
- 超出已批准范围的代码更改、广告格式/位置变更、第三方脚本行为。
用户对某一步的批准只覆盖计划中明确写出的项目、文件、分支、域名和副作用；实质变更需重新确认。

### 机密与第三方内容
不得在 Agent 运行记录和报告中写密码、OAuth/token、私钥、API key 或 cookies。只记录凭证存在性和必要状态。广告脚本、下载的网页和调研材料按不可信输入处理，不在本地预览中执行真实广告代码。

## 9. Agent 级完成标准
一次完整新站运行须满足：
1. 本轮 Skill 版本及契约可追溯。
2. 本轮必需输入、来源和报告路径清晰。
3. 模板源未被修改，目标站内容没有未处理的旧身份/URL 残留。
4. 内容按研究事实构建，内页关键词与素材关系完整；未确认项已列出。
5. 生产构建与全站上线前检查有当前 commit 的证据。
6. 部署前用户看过具体计划并明确批准所有外部变更。
7. 部署、GSC、GA4 的服务状态分别核验并如实报告；有广告时，真实部署后完成广告验收或标记阻断/局限。
8. 总结报告能让用户知道已完成、未完成、证据位置、下次恢复点和仍需人工处理的事项。

## 10. 已确认约束与当前待定项
