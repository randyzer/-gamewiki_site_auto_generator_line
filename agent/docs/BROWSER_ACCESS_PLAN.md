## 第三轮代码修正

复审发现旧版工具服务将有效的 `scoped-bsk-launch` 当作命令批准，此语义已移除。启动许可只验证能否启动服务，不批准任何命令。命令批准必须由宿主能力提供，包含 `runId`、`stage`、精确 `commandDigest`、`approvedBy`、批准时间、有效期及一次性 `executionId`；重复使用、参数变化、错阶段和过期均拒绝，执行标识在执行前持久化占用。

当前 Codex 的命令审批由当前对话的工具执行环境处理，没有向这个 stdio 子进程提供受支持的审批接口。生产入口不注入审批回调，不读取 worker 提供的批准记录；命令返回 `APPROVAL_CAPABILITY_UNAVAILABLE`。`skill-executor` 即使收到有效启动许可，也在启动浏览器 worker 前返回 BLOCKED。没有实现或启用自动审批替代方案。

第四轮进一步关闭默认入口：对于阶段 0、1、4、5，无论是否传入启动许可、许可是否有效，都在 worker 启动前返回 `APPROVAL_CAPABILITY_UNAVAILABLE`；非浏览器阶段保留原沙箱执行路径。提示中不再要求 worker 直接调用 bsk。

服务初始化不会额外调用真实 bsk。离线协议测试注入明确标记的 fake bsk，验证初始化、固定工具列表、逐条审批请求、持久化去重、错误脱敏及独立清理审批。窗口创建后必须显式请求 `tab list`；不会暗中追加真实浏览器调用。

公开采集不再读取 `document.body.innerText`。目前仅支持 Steam APP2406770 的标准 JSON-LD `VideoGame`/`Product`：实际页面 URL、唯一 Bodycam 名称与游戏 URL 必须匹配，输出只包含指定公开字段。没有匹配数据、身份改变或其他未定义内容结构时拒绝采集。该兼容性仅通过离线 fixture 验证；尚未重访真实 Steam 页面，不能说新提取器已通过真实网页联调。

宿主还会独立校验 `STEAM_PUBLIC_GAME_JSON_LD_V1`、实际 URL、APP 2406770、Bodycam 名称、字段类型和长度，重新构建公开输出并丢弃原始正文、额外字段、controls 及任意外层 JSON。净化后的结果才会转发和保存到命令审计；格式缺失或不匹配返回 `PUBLIC_CONTENT_UNVERIFIED`。关闭窗口仍须独立批准；没有批准时保留清理失败状态，不追加自动清理权限。

此只读联调不启动自动审批子进程，也不启用文件上传下载或网站发布。以下受控接口设计保留为代码成果，其真实服务尚未获准启动，且缺少宿主逐命令审批能力；不能把只读联调批准解释为整个接口或七阶段发布流程已获准。

原始方案的 `--approve-for-me` 子进程启动被自动审批拒绝：审批无法证明子进程只执行一条只读 bsk status。该方案已停止，没有使用全局危险权限，也没有改用其他浏览器或公开搜索。
